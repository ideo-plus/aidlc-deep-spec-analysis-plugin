# ドメインオブジェクトの種類を明確にする

## 基本となる種類

| 種類 | 責務 |
| --- | --- |
| エンティティ | IDによる同一性を持つ。集約ルートと、集約内のローカルエンティティを区別する |
| 値オブジェクト | 値の意味で等価性が決まる不変の型。Domain Primitiveを含む |
| ファーストクラスコレクション | 要素の集合、操作、順序や一意性などの不変条件を所有する |
| ドメインイベント | 起きた出来事を不変の記録として表す |

集約は種類を一つ追加するものではなく、ルートと所有する要素からなる整合性境界である。コレクションからIDで識別される要素は、既存の識別規律に従ってエンティティとして設計する。

2026-09-05の追加裁定: ファーストクラスコレクションはドメイン固有の要素型を内包し、プリミティブ型の配列・集合を包むだけのものを認めない。`ErrorMessages`は`ErrorMessage[]`を持ち、`of`・`add`も`ErrorMessage`を受け取る。過去の「文言・列挙値はプリミティブのままでよい」という除外は撤回する。共通原則の正本は各ハーネスの`knowledge/aidlc-shared/first-class-collections.md`。

## 型を置く前の確認

1. 同一性をIDで決めるか、値の意味で決めるかを明確にする。
2. 配列やMapの操作を、呼び出し側が繰り返していないか確認する。
3. 判断・構築・導出を所有する型を決める。判断の結果そのものは値オブジェクトになり得る。
4. `Manager`・`Helper`・`Context`など、手続きをまとめただけの型を便利さだけで追加しない。

ドメインサービスの新設や、既存の種別では説明できない新しい型には、問題が起きているコードと対策の根拠が必要である。人間の裁定に関する既存のproject規則を維持する。既に承認された型を名前だけで不適切と断定しない。

ドメインイベントを導入する場合は、イベント自身の同一性と対象の集約IDを混同しない。本規則はイベントの保存方式や、すべてのコマンドからイベントを返すことを要求しない。
適用範囲と優先関係は[共有規則の入口](README.md)を参照。
